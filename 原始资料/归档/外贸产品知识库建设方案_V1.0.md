# 外贸产品知识库建设方案 V1.0

> 适用场景：约 400 种产品、其中不足 100
> 种为重点推广产品；个人维护；资料格式多样；本地存储；通过 Claude Code
> 辅助 WhatsApp 客户回复。\
> 方案原则：先把资料整理成可检索、可信任的知识，再逐步自动化；不在第一阶段引入不必要的服务器、向量数据库或模型
> API。

------------------------------------------------------------------------

## 1. 建设目标与总体建议

### 1.1 当前情况

  项目           当前情况
  -------------- ------------------------------------------------
  产品总量       约 400 种
  主推产品       不到 100 种
  资料形式       Excel、PDF、Word、图片、网页资料等多种形式
  维护方式       现阶段主要由本人维护
  存储要求       本地存储
  AI 使用方式    Claude Code 读取知识库，辅助 WhatsApp 客户回复
  当前阶段目标   先建立可靠的产品知识库，不急于开发完整客服系统

### 1.2 推荐方案

**推荐采用：Obsidian + 本地 Markdown + 原始资料目录 + Claude Code。**

-   **Obsidian**：作为知识库的可视化管理界面，方便浏览、编辑、链接和查看产品资料。
-   **Markdown**：作为标准知识内容格式，Claude Code 可以直接读取。
-   **原始资料目录**：保存原始
    Excel、PDF、Word、产品图片、图纸、证书等，避免只保留 AI
    整理后的内容。
-   **Claude
    Code**：根据客户问题搜索相关产品资料，整理依据并生成回复草稿。

第一阶段不强制安装
Baserow、Notion、向量数据库或其他在线知识库服务。等产品数据结构和实际检索需求稳定后，再判断是否需要增加数据库。

### 1.3 为什么不建议一开始把 400 种产品全部写成详细文档？

产品数量多不等于每个产品都需要投入同样的整理成本。

建议分层管理：

  产品层级                      数量 管理方式                    整理深度
  ------------------ --------------- --------------------------- ----------------------
  A 类：主推产品         不足 100 种 独立产品知识文档            详细
  B 类：普通产品       其余约 300 种 产品主清单 + 原始资料索引   基础
  C 类：待确认产品      数量动态变化 待整理清单                  暂不作为可靠回答依据

A 类产品随着销售情况动态调整。某个 B 类产品成为主推产品时，再升级为 A
类。

## 2. 软件与工具选择

### 2.1 核心软件

  ---------------------------------------------------------------------------------------------
  工具                    用途                                         是否必需
  ----------------------- -------------------------------------------- ------------------------
  Obsidian                本地知识库浏览、编辑、链接和管理             推荐

  Claude Code             搜索知识、读取资料、整理内容、生成回复草稿   已有工作流

  Excel                   原始产品目录、批量数据整理                   按现有情况使用

  PDF/Office 阅读软件     查看原始规格书、报价资料、图纸               按需

  Git                     版本管理、回滚误修改                         推荐，但可第二阶段配置
  ---------------------------------------------------------------------------------------------

Obsidian 官方网站：https://obsidian.md/

### 2.2 为什么选择 Obsidian？

1.  知识库存储在本地文件夹中，不依赖在线服务才能访问。
2.  Markdown 是普通文本格式，Claude Code 可以直接读取。
3.  可以通过链接把产品、分类、FAQ、技术说明关联起来。
4.  可以逐步增加标签、属性和数据库式视图。
5.  即使以后更换知识库软件，Markdown 文件仍然可以继续使用。

注意：Obsidian
是知识库管理界面，不是自动替你完成资料清洗的工具。原始资料仍需要整理、核实和建立索引。

### 2.3 第一阶段暂不引入的技术

-   向量数据库
-   独立 RAG 服务
-   自建后端 API
-   在线知识库 SaaS
-   多模型 API 调度
-   复杂自动化工作流

原因：当前核心问题是资料分散、字段不统一、产品信息缺少可信来源，而不是检索算法不够先进。先解决数据质量，再考虑技术升级。

### 目录管理原则

1.  原始资料和整理后的知识分开保存。
2.  一个产品使用一个稳定且唯一的产品编号。
3.  文件名优先使用"产品编号_简短名称"，不要只用容易重复的产品名称。
4.  产品分类可以调整，但产品编号尽量不变。
5.  不要把客户隐私、账号密码、付款凭证等无关敏感信息放入供 AI
    随意检索的知识库。
6.  重要文件定期备份，不能把 Obsidian 同步功能误认为备份。

## 4. 产品数据如何设计

产品总清单是整个知识库的入口。建议先整理全部 400
种产品的基础信息，再逐步完善重点产品。

### 4.1 产品主数据字段

建议在 Excel 中建立以下字段：

  字段                 示例                         说明
  -------------------- ---------------------------- ----------------------------
  product_id           JS-001                       唯一编号，不重复
  product_name_cn      街机摇杆                     中文名称
  product_name_en      Arcade Joystick              英文名称
  category_l1          Arcade Parts                 一级分类
  category_l2          Joystick                     二级分类
  category_l3          8-Way Joystick               三级分类，可选
  model                JS-001                       型号
  product_status       Active                       在售、停产、待确认
  priority             A                            A 主推 / B 普通 / C 待整理
  application          Arcade Machine               应用场景
  keywords             joystick, arcade             搜索关键词
  source_files         06_原始资料/PDF/JS-001.pdf   原始资料路径
  knowledge_file       02_产品知识/摇杆/JS-001.md   详细知识文档路径
  last_verified        2026-11-18                   最近核实日期
  information_status   Verified                     信息状态
  owner_notes          需确认接线方式               内部备注

字段可以根据实际业务调整，不必一开始全部填满。

### 4.2 产品状态与主推等级要分开

例如：

-   `product_status`：在售、停产、暂时缺货、待确认。
-   `priority`：A 主推、B 普通、C 待整理。

一个产品可以是"在售但非主推"，也可以是"主推但部分参数待确认"。不要把这两个概念合并成一个字段。

### 4.3 产品变体如何管理

同一产品可能有不同尺寸、颜色、电压、接口或包装版本。

建议区分：

-   产品系列：同一类产品的集合。
-   产品型号：可独立识别的产品。
-   产品变体：同一型号下的具体规格组合。

如果不同规格会影响兼容性、价格或安装方式，就应当单独记录变体，不要让 AI
把不同规格混为一谈。

## 6. 多种格式的产品资料如何处理

你的资料来源比较复杂，不建议全部强行转换成 Markdown。应当采用"原件保留 +
关键内容提取 + 统一索引"的方式。

  原始格式       建议处理方法                                       是否保留原件
  -------------- -------------------------------------------------- --------------------
  Excel          先检查表头、重复型号和字段含义，再整理到主数据表   保留
  PDF 规格书     提取参数、适用条件、注意事项，并记录页码           保留
  Word           提取产品介绍、技术说明、政策内容                   保留
  JPG/PNG 图片   按产品编号命名，记录视图和用途                     保留
  CAD/工程图     保留原始图纸，提取关键尺寸并注明图纸版本           保留
  产品视频       记录视频路径、内容摘要和时间点                     保留
  网页资料       保存来源网址、访问日期和关键内容                   建议保存副本或摘要

### 图片管理建议

例如：

``` text
06_原始资料/产品图片/
└── JS-001/
    ├── JS-001-front.jpg
    ├── JS-001-side.jpg
    ├── JS-001-installation.jpg
    └── JS-001-detail.jpg
```

图片名称要能与产品编号对应。

### 来源追踪规则

提取参数时尽量记录：

-   来源文件名
-   PDF 页码或 Excel 工作表名称
-   原始资料版本
-   核实日期
-   核实人或确认方式

如果两个文件中的参数不一致，不要让 Claude
自行选择一个。应将冲突放入待核实清单。

## 7. 信息可信度与 AI 回复安全规则

这是外贸知识库最重要的规则之一。

### 7.1 信息状态

建议统一使用以下状态：

  状态         含义               AI 使用规则
  ------------ ------------------ ------------------------
  Verified     已经确认           可以作为明确事实回答
  Partial      部分确认           只能回答已确认部分
  Unverified   尚未核实           不得当作确定事实
  Conflicted   不同资料存在冲突   停止判断，要求人工核实
  Deprecated   已过期或停用       不作为当前业务依据

### 7.2 不同信息的处理规则

**产品参数**

-   没有资料支持的尺寸、电压、材质、寿命，不得编造。
-   兼容性必须有型号、接口、尺寸等依据。
-   客户发来图片时，可以提出可能的产品方向，但不能仅凭外观保证完全兼容。

**价格与交易政策**

-   不允许根据历史报价自行推算当前报价。
-   不允许自行承诺折扣、MOQ、交期、付款条件。
-   没有最新有效政策时，应询问客户需求并交由人工确认。

**客户沟通**

-   不清楚客户需求时，优先提出一个有针对性的问题。
-   回复尽量简洁、自然，不要一次发送大量产品说明。
-   投诉、质量争议、退款、索赔、付款异常、法律合规问题交由人工处理。

## 8. Claude Code 如何读取知识库

### 8.1 CLAUDE.md 的职责

`CLAUDE.md` 不应该复制全部产品知识，而是告诉 Claude：

1.  知识库在哪里。
2.  产品编号如何使用。
3.  如何查找产品。
4.  信息可信度如何判断。
5.  哪些问题必须人工确认。
6.  回复 WhatsApp 客户时遵循什么规则。

建议初始内容：

``` markdown
# Export Sales Knowledge Base

## Role
You are an assistant for an international sales team
selling arcade machine parts and related products.

## Knowledge Sources
- Product master data: ./01_产品主数据/
- Product knowledge: ./02_产品知识/
- Company and sales policies: ./03_公司与销售政策/
- FAQ and sales playbook: ./04_FAQ与销售话术/
- Technical and application documents: ./05_应用与技术资料/
- Original source files: ./06_原始资料/
- Unverified information: ./08_待核实信息/

## Retrieval Rules
1. Identify the customer's product, model and intent first.
2. Search the product master list using product name,
   model, category and keywords.
3. Open only the relevant product documents.
4. Check the information status and source.
5. Consult sales policies separately when discussing
   price, MOQ, samples, delivery or payment.
6. Do not treat historical chat examples as authoritative
   product specifications or current commercial policies.

## Accuracy Rules
- Never invent specifications, prices, MOQ or lead times.
- Never claim compatibility without sufficient evidence.
- Clearly distinguish verified and unverified information.
- If sources conflict, stop and request human confirmation.
- Never fill missing data with assumptions.

## WhatsApp Reply Style
- Use the customer's language when possible.
- Use natural, concise and professional business language.
- Answer the actual question first.
- Ask a relevant follow-up question when necessary.
- Avoid excessive promotional language.
- Do not send a message unless the user explicitly
  authorizes the sending action.

## Human Escalation
Escalate complaints, refunds, quality disputes,
custom technical requirements, special discounts,
contract terms and uncertain commitments to a human.
```

### 8.2 推荐检索流程

不要每次把 400 种产品的全部资料交给 Claude。

正确流程：

1.  读取客户 WhatsApp 消息。
2.  判断客户意图：产品咨询、询价、兼容性、定制、订单、售后等。
3.  从产品总清单搜索型号、名称、关键词。
4.  定位相关产品文档。
5.  读取相关技术资料或图片。
6.  如果涉及 MOQ、价格、交期，再读取对应销售政策。
7.  检查信息状态和来源。
8.  生成英文回复草稿。
9.  初期由人工审核后发送。

### 8.3 检索不到时怎么办？

-   不要随意扩大解释。
-   不要拿相似产品的参数冒充目标产品参数。
-   记录客户原始问题。
-   将缺失资料加入待核实清单。
-   人工确认后再更新知识库。

## 9. 知识库如何持续更新

知识库不是一次性项目，而是随着客户沟通不断完善的业务资产。

建议采用以下闭环：

``` text
客户提出问题
      |
      v
Claude 查询知识库
      |
      v
找到准确答案了吗？
   /          \
  是           否
  |             |
生成回复草稿   记录缺失信息
  |             |
人工审核       人工核实
  |             |
发送回复       更新知识库
  |             |
  +------<------+
      |
      v
沉淀优秀问答案例
      |
      v
定期整理 FAQ 和销售话术
```

### 更新规则

-   新产品：先登记产品主数据，再建立产品文档。
-   产品参数变化：更新产品文档，同时记录来源和日期。
-   价格政策变化：更新销售政策，不要只修改聊天案例。
-   新客户问题：先记录，确认答案后再加入 FAQ。
-   停产产品：标记为 Deprecated 或停产，不要直接删除历史资料。
-   重要修改：记录在 CHANGELOG.md 中。

建议每周花一点时间处理待核实信息和新出现的高频问题。

## 10. 分阶段实施计划

### 第一阶段：建立知识库骨架

目标：先让本地文件结构稳定。

1.  安装 Obsidian。
2.  创建知识库目录。
3.  创建上述目录结构。
4.  创建 README.md、CLAUDE.md。
5.  建立产品分类标准和字段标准。
6.  确认产品编号规则。

**验收标准：** Obsidian 能正常打开本地知识库，Claude Code
能读取项目文件。

### 第二阶段：整理 400 种产品基础清单

目标：建立统一产品入口。

1.  收集现有产品 Excel。
2.  统一产品编号和名称。
3.  统一产品分类。
4.  标记 A/B/C 优先级。
5.  关联已有规格书和图片路径。
6.  标记重复、停产、缺失和冲突数据。

**验收标准：**
每种已知产品都能通过编号或关键词定位；不要求每种产品都已有完整参数。

### 第三阶段：完善主推产品

目标：先完成实际会被客户询问的产品。

1.  挑选第一批 10--20 种主推产品。
2.  按详细模板建立文档。
3.  关联产品图片和原始规格书。
4.  核实关键参数。
5.  整理常见问题。
6.  记录尚未确认的信息。

**验收标准：** Claude 能根据客户问题找到正确产品，并且不会混淆相近型号。

### 第四阶段：销售知识建设

目标：让 Claude 不仅懂产品，也懂业务规则。

整理：

-   公司介绍
-   OEM/ODM 能力
-   MOQ
-   样品政策
-   报价流程
-   付款方式
-   生产周期
-   运输方式
-   售后政策
-   英文沟通风格

**验收标准：**
涉及交易承诺的问题能正确引用政策；没有依据时能主动询问或转人工。

### 第五阶段：接入 WhatsApp 辅助回复

目标：从人工审核模式开始。

1.  测试客户消息读取。
2.  测试产品检索。
3.  测试英文回复生成。
4.  测试多语言理解。
5.  测试型号相似、参数缺失、客户发图等场景。
6.  由人工审核并发送。
7.  记录错误和知识缺口。

**验收标准：** 回复有依据、型号不混淆、不会擅自报价或承诺。

### 第六阶段：持续优化

当产品资料、检索流程和回复质量稳定后，再考虑：

-   Baserow 等结构化数据库
-   自动化资料导入
-   图片辅助检索
-   专门的检索服务
-   客户信息与跟进管理
-   WhatsApp Business Platform 官方接口

是否升级应由真实使用中的瓶颈决定，而不是为了追求技术复杂度。

## 11. 测试标准

正式用于客户回复之前，至少准备以下测试问题：

  测试场景           预期表现
  ------------------ ------------------------------------
  客户询问某个型号   找到对应产品文档
  客户只说产品俗称   根据关键词定位候选产品，并确认型号
  两款产品外观相似   不混用参数
  客户询问电压       只引用已核实的电压
  客户询问价格       按报价政策处理，不自行编造
  客户询问 MOQ       引用有效政策，没有则转人工
  客户询问能否兼容   根据接口、尺寸和设备信息判断
  客户发送产品图片   可以辅助识别，但不凭外观保证型号
  客户要求特殊定制   收集需求，交由人工确认
  客户投诉           不自动承诺退款或赔偿
  找不到产品资料     明确说明需要进一步确认

建议记录每次测试的客户问题、检索到的资料、AI 回复、错误原因和修正结果。

## 12. 备份与数据安全

1.  知识库目录应定期备份到另一块磁盘或可信的备份位置。
2.  可以使用 Git 管理 Markdown、配置文件和模板的版本。
3.  产品图片、PDF、视频等大文件应有独立备份策略。
4.  不要把密码、WhatsApp 登录凭证、API 密钥放入知识库或 Git 仓库。
5.  如果把资料交给 Claude
    处理，应先检查团队订阅对应的数据使用和管理政策，并避免上传不必要的客户隐私。
6.  本地存储不代表所有 AI 处理都在本地完成；Claude
    读取并处理的内容可能会发送到相应云端服务，应按公司资料保密要求决定哪些文件可以提供给模型。

### 最重要的实施原则

**先统一产品数据，再整理详细知识；先保证答案准确，再追求自动回复速度。**

第一阶段的成功标准不是"Claude 能读取 400 种产品"，而是：

1.  能快速找到正确产品。
2.  能准确回答已确认的产品问题。
3.  不会把不同型号和规格混淆。
4.  不会编造价格、MOQ、交期和兼容性。
5.  不知道答案时，能明确提出需要确认的信息。

达到这些标准后，再逐步扩大产品覆盖范围和自动化程度。
